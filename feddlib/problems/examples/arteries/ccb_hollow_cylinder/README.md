# CCB hollow-cylinder comparison

Cross-check case for svMultiPhysics's Interface2/AceGen CCB constrained-mixture
element test (`tests/cases/def_diffu/hollow_cylinder` in the svMultiPhysics
repo). Same geometry, same shared material parameters, same BC scheme, same
load ramp -- run through FEDDLib's own Trilinos/NOX/Belos/FROSch solver stack
instead of svMultiPhysics's FSILS/GMRES, to see whether the same
load-driven, near-equilibrium-prestretch problem converges differently.

## Why this exists

svMultiPhysics's own equivalent element (the CMM/constrained-mixture variant)
doesn't exist in FEDDLib, so this uses the non-CMM sibling
(`SCI_SMC_Active_Growth_Reorientation`) instead -- the two models share most
parameter names/roles (Alpha1-5, fA, etc, set to identical values here) but
are not numerically identical. **This is not meant to reproduce identical
numbers** -- a finite-difference check already confirmed the CMM kernel's own
tangent is exact (worst relative error 1.3e-7 across 1700 Kuu/Kuc/Kcu/Kcc/Mc
entries, independent of FEDDLib entirely). What this checks is *convergence
behavior*: does the same kind of problem (a load-driven passive hyperelastic
solve starting from a state that needs a large-ish nonlinear correction just
to reach the model's own no-load equilibrium) behave differently under
FEDDLib's solver stack.

All `*Bool` material flags are 0 (purely passive, load-driven response only).

## Build

From a configured Trilinos+FEDDLib(+Interface2/AceGenInterface) build
directory:

```
make ccb_hollow_cylinder
# or: make -j <N>   (builds everything, this target included)
```

## Run

```
cd <build_dir>/feddlib/problems/examples/arteries/ccb_hollow_cylinder
mpirun -np 4 ./ccb_hollow_cylinder.exe 2>&1 | tee run.log
```

(Exact binary name may be `problems_ccb_hollow_cylinder.exe` or similar
depending on TriBITS target aliasing in this build -- check
`ctest -N | grep ccb_hollow_cylinder` if `ccb_hollow_cylinder.exe` isn't
found next to the copied XML/mesh files.)

## What to send back

1. **`run.log`** in full -- `solverParameters.xml` has been set to print
   NOX's per-Newton-iteration outer status (`Outer Iteration`,
   `Outer Iteration StatusTest`) and Belos's per-linear-solve details
   (`Linear Solver Details`, `Inner Iteration`), so this should contain a
   directly comparable record to svMultiPhysics's own convergence log (10
   load steps, Newton residual per iteration, GMRES iterations/residual per
   linear solve).
2. Whether the run completes all 10 (or however many actually run before
   failing, if it fails) load steps.
3. If it's easy to grab: the exported Paraview/VTK output showing the final
   deformed shape, to visually cross-check against svMultiPhysics's result
   (should be an axisymmetric radial expansion; svMultiPhysics's own run
   shows the model's own material parameters implying a large, load-
   independent ~17% radial prestretch even before any pressure is applied --
   worth checking whether that same behavior shows up here too, since that
   would confirm it's a property of the material parameters rather than
   svMultiPhysics-specific).

## Mesh / BC flags

See `feddlib/meshes/ccb_comparison/hollow_cylinder_p1.mesh` (P1, FEDDLib
builds its own P2 enrichment internally) and the comment block at the top of
`main.cpp` for the face/vertex flag scheme (bottom/top axial fix, 3
circumferential pins, ramped inner-wall pressure). Both were generated by
`generate_feddlib_mesh.py` in svMultiPhysics's own
`tests/cases/def_diffu/hollow_cylinder/` directory, from the exact same
gmsh geometry (Ri=1.0, Ro=1.3, L=2.0) svMultiPhysics's test uses.
